# ADR-001 — AWS CDK as the Infrastructure as Code Source of Truth

Status: Accepted
Date: 2026-08-09

## Context

CommerceOS is a multi-tenant serverless learning project that will use multiple AWS managed services across local, dev, preview, staging, and eventually production environments.

The project is developed with AI agents under a Harness Engineering workflow. Infrastructure therefore needs to be reproducible, reviewable, machine-verifiable, cost-aware, and understandable from the repository itself.

Manual AWS Console setup would create hidden state, drift, inconsistent environments, and poor reviewability. It would also make it harder to automatically create/destroy ephemeral environments while preserving the Free Tier / approximately USD 100 credit budget.

## Decision

Use **AWS CDK** as the application Infrastructure as Code system for CommerceOS.

All application AWS resources must be represented in version-controlled CDK code unless an explicit documented exception exists.

CDK synthesizes CloudFormation and deployment pipelines deploy the synthesized infrastructure through environment-specific AWS IAM roles.

The AWS Console is not an infrastructure source of truth.

The concrete CDK implementation language will be selected in Phase 0 together with the application/toolchain structure.

## Alternatives considered

### Manual AWS Console

Rejected as the primary method because it is not reproducible, is difficult for agents/CI to validate, and encourages configuration drift.

### Raw CloudFormation

Viable and is the deployment substrate generated by CDK, but less attractive for this project because reusable constructs, testing, programming abstractions, and agent-maintainable infrastructure code are central learning goals.

### Terraform / OpenTofu

Strong general-purpose alternatives. Not selected initially because CommerceOS intentionally focuses on AWS serverless architecture and CDK provides direct AWS-native constructs/integration while still teaching Infrastructure as Code principles.

A later migration would require a new ADR and explicit state/migration plan.

### AWS SAM only

Useful for Lambda/serverless local workflows and may be used as a development/testing tool, but not selected as the overall infrastructure source of truth because CommerceOS also includes Cognito, CloudFront, DynamoDB, EventBridge, SQS, Step Functions, crawler infrastructure, and environment/cost governance.

## Consequences

Positive:

- Git contains the desired AWS architecture;
- preview/staging can be created and destroyed consistently;
- IaC changes are reviewable through `cdk diff`;
- reusable cost-safe constructs can encode Free Tier defaults;
- CI can run synth/assertion/security checks;
- infrastructure and application changes can share task/PR context;
- agents can reason about AWS resource dependencies from repository code.

Negative/trade-offs:

- CDK/CloudFormation become project dependencies;
- developers must understand deployment/update/replacement semantics;
- bootstrap configuration is required per AWS environment;
- stateful resource changes still require migration/protection planning;
- CDK abstraction must not hide understanding of the AWS services underneath.

## Security and tenant impact

- Deployment roles use GitHub Actions OIDC rather than long-lived AWS access keys.
- Roles are environment-specific and least-privileged.
- IAM policies, Cognito configuration, table policies, bucket policies, and tenant-security-sensitive infrastructure become reviewable code.
- Manual administrator-level deployment shortcuts are prohibited as normal workflow.

## Reliability and operability impact

- Environment creation/update is repeatable.
- CloudWatch/logging/alarm defaults can be encoded centrally.
- Preview environments can be automatically cleaned up.
- Stack/resource tagging enables cost attribution and operational discovery.
- Stateful resources use environment-appropriate removal/protection policies.

## Cost impact

AWS CDK itself does not justify introducing paid always-on infrastructure. The deployed AWS resources determine cost.

The CDK layer must encode Free Tier/credit guardrails including:

- no NAT Gateway/ALB/EC2/RDS by default;
- small DynamoDB non-prod capacity profiles where appropriate;
- short non-prod log retention;
- bounded Lambda concurrency;
- crawler schedules disabled/manual by default outside explicit tests;
- S3 lifecycle/ephemeral cleanup;
- standard cost tags.

Any new service/resource with material recurring cost requires task cost analysis and, when architectural, another ADR.

See `../development/13-free-tier-and-credit-guardrails.md`.

## Reversibility / migration

The decision is reversible but not free once environments become substantial.

Moving to Terraform/OpenTofu/raw CloudFormation would require:

1. inventory of CDK-managed resources;
2. state/import/recreation strategy;
3. protection of DynamoDB/S3/stateful resources;
4. parallel validation in non-production;
5. explicit cutover/rollback plan.

Because CDK synthesizes CloudFormation, knowledge of the underlying resources remains portable even if tooling changes later.

## Validation

Phase 0 must demonstrate:

- a clean checkout can `cdk synth` the skeleton environment;
- `cdk diff` produces reviewable infrastructure changes;
- GitHub Actions can authenticate via OIDC to a non-prod deployment role;
- a small dev/preview stack can be deployed from CDK;
- an ephemeral stack can be destroyed without hidden manual dependencies;
- no application resource required by the skeleton exists only through undocumented Console setup.
