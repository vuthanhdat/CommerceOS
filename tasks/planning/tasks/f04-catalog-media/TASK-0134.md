## Objective
Let Catalog accept an explicitly approved source candidate through a producer-owned command while preserving canonical validation and one-to-one Tenant source mapping.

## Scope
`ApplyImportCandidate`/source-link contract; source-idempotency; Tenant source-product claim; selected field application; Catalog validation; provenance; success/failure response used by PDI to mark Applied.

## Out of scope
Catalog reading PDI table, automatic source refresh mutation, source media republication.

## Inputs
Catalog/PDI domain baselines and CAT-AP-13/18.

## Expected changes
Catalog Application/Infrastructure/Contracts plus tests.

## Implementation steps
Define minimal producer-owned apply DTO; validate Tenant/current Product/lifecycle/fields; transactionally enforce mapping/idempotency/revision; return accepted result without owning candidate state.

## Acceptance criteria
- [ ] Catalog never reads PDI persistence.
- [ ] Only explicit approved apply intent can mutate canonical Product.
- [ ] Imported fields pass the same validation/lifecycle rules as manual edits.
- [ ] One source-product identity maps to at most one Product per Tenant.
- [ ] Replay does not duplicate mutation/provenance; incompatible reuse conflicts.
- [ ] Catalog acceptance is distinct from PDI `Approved`; PDI marks `Applied` only after success.

## Verification
Contract/domain/persistence/tenant isolation/replay/harness.

## Architecture / security / reliability / observability / local runtime
Source identity is data, not Tenant authority. Preserve correlation/causation/provenance.

## Risks and edge cases
Candidate becomes stale while Product revision changes.

## Open questions
None.

Completed 2026-08-14. Added producer-owned `ApplyApprovedImportCandidate` contract and Catalog transactional import/source mapping records. Catalog accepts only explicit commands, does not read PDI persistence, applies standard Product validation, and records candidate/source claims for replay/conflict safety.
