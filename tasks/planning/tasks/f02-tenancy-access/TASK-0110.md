## Objective
Create the Tenancy implementation boundary and Tenant/Membership persistence foundation required by approved access patterns.

## Context
Tenant Management and Merchant Access are separate business areas hosted in one implementation module/table so local invariants can be transactional.

## Scope
Domain/Application/Infrastructure module structure; Tenant/Profile, Membership/authority/discovery/guards persistence ports and DynamoDB mapping; access-pattern ledger; tenant-scoped repository contracts.

## Out of scope
Full onboarding, invitations, authorization UX, Subscription implementation, platform lifecycle commands.

## Inputs
Tenant domain baseline, ADR-004/005, persistence access patterns.

## Expected changes
New Tenancy module projects/registration, module-owned CDK table only when named by this task; exact paths after code inspection.

## Implementation steps
Create module boundary, model approved core records, define tenant-scoped ports, implement key/access patterns without Scan, add LocalStack persistence tests and architecture references.

## Acceptance criteria
- [x] Tenancy owns its persistence and no other module can use private repository/key models.
- [x] Tenant-owned methods require trusted scope; no unscoped merchant overload.
- [x] Subject discovery representation is candidate discovery only.
- [x] Conditional/revision primitives exist for later lifecycle writes.
- [x] Access-pattern ledger documents consistency/isolation/recovery/cost amplification.
- [x] LocalStack DynamoDB verification passes.

## Verification
Unit/architecture/persistence integration/CDK synth/LocalStack/harness.

## Architecture / security / reliability / observability / local runtime
TenantId in keys is not authorization by itself. Strong/current paths available for authority decisions. Correlation-safe repository diagnostics only.

## Risks and edge cases
Do not over-model future closure/deletion; no cross-domain transaction.

## Open questions
None material for module foundation.

## Completion report
Completed on 2026-08-13.

### Implementation

- Added isolated `CommerceOS.Tenancy.Domain`, `.Application`, and
  `.Infrastructure` projects, each following the required dependency direction.
- Defined Tenant/Profile, Membership, role/status, and opaque identifiers in the
  Domain. The Application persistence port requires
  `TrustedTenantPersistenceScope` for every tenant-bound read/write; only subject
  discovery accepts an authenticated Subject and returns explicit candidates.
- Added the module-private DynamoDB adapter with encoded key construction,
  strongly consistent reads, candidate discovery Query, and conditional create /
  expected-revision write outcomes.
- Added `TenancyTable` to the FoundationStack with task-prefixed name, `PK/SK`,
  pay-per-request billing, managed encryption, and profile-controlled removal.
  The LocalStack launcher now enables DynamoDB for this named capability.
- Added the module-local [access-pattern ledger](../../../../src/Modules/Tenancy/ACCESS-PATTERNS.md).
