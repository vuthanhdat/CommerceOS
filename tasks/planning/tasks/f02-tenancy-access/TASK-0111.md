## Objective
Resolve current Tenant authority from authenticated subject + selected eligible Membership and return distinct read versus mutation contexts.

## Scope
`DiscoverMerchantTenants`, `ResolveTenantReadAuthority`, `ResolveTenantMutationAuthority`; multi-membership selection rules; current Tenant/Membership validation; Active/Suspended behavior; non-disclosing failures.

## Out of scope
Identity-provider provisioning details, authorization by JWT role/tenant claims, platform bypass context.

## Inputs
ADR-004, first-frontier contracts, tenant domain baseline.

## Expected changes
Tenancy Application contracts/services and delivery adapter integration after code inspection.

## Implementation steps
Model principal/selection inputs, implement strong current authority resolution, separate read/mutation result types, add cross-Tenant and stale-membership tests.

## Acceptance criteria
- [x] Client tenantId/SubjectId/token role claims cannot grant Tenant authority.
- [x] One eligible Tenant may auto-select; multiple require intentional selection.
- [x] Active Membership is required.
- [x] Read context permits Active/Suspended according to policy; mutation requires Active Tenant.
- [x] Disabled Membership and cross-Tenant known IDs fail closed/non-disclosing.
- [x] Current role/status changes affect subsequent resolution without relying on token freshness.

## Verification
Unit + LocalStack Tenancy integration + cross-tenant tests + architecture/harness.

## Architecture / security / reliability / observability / local runtime
This is a security boundary. Log correlation/outcome, never raw tokens or cross-Tenant private identifiers in merchant-visible errors.

## Risks and edge cases
Concurrent Membership/Tenant changes; ambiguous selection; stale cache must not become authority.

## Open questions
Identity edge may use test adapter if LocalStack Cognito is insufficient, preserving same principal contract.

## Completion report
Completed 2026-08-13.

- Added transport-neutral authenticated-principal, requested-selection, discovery, failure, and distinct trusted read/mutation authority contracts in Tenancy Application.
- Resolution obtains candidate Tenants through the strongly consistent subject discovery port and revalidates current Tenant plus Membership-by-Subject before issuing a context. Unknown selected Tenant IDs and persistence errors fail closed without identifiers in the failure result.
- Added atomic Membership persistence for the Membership, authority-by-Subject, and subject-discovery records so the LocalStack store can exercise the current-authority path without a hidden manual record prerequisite.
- Added unit coverage for auto-selection, ambiguous selection, known foreign Tenant IDs, suspension, disabled Memberships, changed role/status, and persistence failure. The configured LocalStack integration test exercises DynamoDB transaction, discovery, and mutation-authority resolution when the declared lifecycle supplies the endpoint/table.
- Delivery integration is intentionally deferred: the API currently exposes only anonymous `/health` and has no merchant authentication adapter or protected merchant route. The authority contract accepts authenticated identity evidence only and is ready for that delivery adapter; no client-provided Subject/Tenant/role input is wired as authority.
