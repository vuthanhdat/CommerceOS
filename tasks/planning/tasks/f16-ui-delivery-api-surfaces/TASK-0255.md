## Objective
Close the largest current UI-facing backend gap: provide complete tenant-scoped Supplier, PurchaseOrder, GoodsReceipt and SupplierInvoice/Payment query/command surfaces needed by Procurement Backoffice.

## Scope
### Suppliers
- List/detail query.
- Create/archive HTTP delivery.

### Purchase Orders
- List/detail query with Supplier summary, line snapshots, total, status, revision.
- Create Draft, update Draft lines/Supplier, submit and cancel according to existing domain policy.
- Do not invent post-submit edit behavior.

### Goods Receipts
- Create Draft receipt for an eligible submitted PO using explicit warehouse per line where required.
- List/detail receipt and correction history.
- Confirm and record compensating correction via existing service.

### Supplier Invoices / Payments
- List/detail SupplierInvoice with expected amount, actual amount, variance status, Supplier reference/date/revision.
- Record invoice, approve variance with trusted authority, record full payment evidence.
- Query payment evidence/status needed by UI.

## Candidate HTTP surface
`/api/v1/procurement/suppliers`, `/purchase-orders`, `/purchase-orders/{id}/receipts`, `/supplier-invoices` with command subresources/actions consistent with existing contracts.

## Acceptance criteria
- [ ] All records are Tenant-owned and cross-tenant access is denied.
- [ ] Supplier fields remain limited to the current approved model; phone/email/address are not invented.
- [ ] Submitted PO commitment remains immutable except approved cancellation semantics.
- [ ] PO line product name/SKU/unit-price snapshots remain historical facts.
- [ ] Receipt confirmation/correction preserves append/compensating evidence and downstream Inventory integration.
- [ ] Invoice variance approval remains explicit and authority-checked.
- [ ] Supplier payment remains attested external-payment evidence, not a real payment-provider integration.
- [ ] List/detail/read models do not read Catalog/Inventory/Accounting private persistence.
- [ ] Focused application/HTTP/LocalStack tests and full harness pass.

## Verification
Procurement domain/application tests, HTTP tenant/authorization/revision tests, Inventory/Accounting integration regressions, LocalStack persistence, full harness.

## Architecture / security / reliability / observability / local runtime
Keep Procurement owner boundaries and immutable downstream evidence. Commands preserve source identity/correlation/idempotency where existing workflows require it. LocalStack only.

## Risks and edge cases
PO edit/submit race, archived Supplier, Product becomes non-purchasable, partial receipt semantics beyond approved baseline, receipt correction over original quantity, duplicate invoice source identity, variance approval race.

## Open questions
If create/update/cancel PO semantics are not fully specified by current domain/product decisions, implement only behavior already inferable from the existing aggregate and surface any material ambiguity instead of inventing a richer purchasing lifecycle.

## Completion report
Record added Procurement commands/queries/endpoints, any constrained ambiguity and verification.
