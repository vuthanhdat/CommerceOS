## Objective
Provide the merchant administration/operations HTTP read and command surfaces required by Business Settings, Storefront Settings, Team, Subscription, Notifications and Audit screens.

## Scope
### Business / Storefront settings
- Read current Tenant BusinessProfile, status, revision and approved storefront slug/public URL metadata.
- Update only approved merchant-editable BusinessProfile fields.
- Add merchant storefront-slug configuration command only according to the resolved globally unique/permanently retired slug policy; do not invent redirects/custom domains.

### Team
- Member list and pending invitation list.
- Issue/resend/revoke invitation.
- Change member role/status with expected revision and last-owner protections.

### Subscription
- Available plan versions.
- Current Trial/paid subscription read model with condition, period, anchor, entitlements, cancel-renewal and pending downgrade.
- Existing activation/upgrade/downgrade/cancel-renewal actions.

### Notifications / Audit
- Notification list/read/ack endpoints bound to current recipient.
- Tenant Audit list endpoint for approved Owner/Admin access with safe evidence DTO.

## Acceptance criteria
- [ ] Tenant/profile/member/subscription reads derive trusted merchant context.
- [ ] Business profile update does not expose platform lifecycle controls.
- [ ] Storefront slug rules remain authoritative and old retired slugs are not silently reused.
- [ ] Team list/invitation/member mutation honors Owner/Admin rules, max-membership entitlement and last Active Owner protection.
- [ ] Subscription UI contract exposes EntitlementSet facts rather than using Plan name as runtime authority.
- [ ] Upgrade/downgrade/cancel flows preserve billing evidence and current usage constraints.
- [ ] Notification state is per current recipient and acknowledge does not resolve source exception.
- [ ] Audit endpoint is Owner/Admin protected and does not leak secret/sensitive payloads.
- [ ] HTTP tenant/role/revision/limit tests and full harness pass.

## Verification
Tenancy/Subscription/Notification/Audit application tests, HTTP security tests, LocalStack persistence, full harness.

## Architecture / security / reliability / observability / local runtime
Do not combine merchant support authority with Platform Admin authority. Notification/Audit are evidence/read surfaces, not business correction mechanisms. LocalStack only.

## Risks and edge cases
Last-owner change, invite resend credential rotation, subscription usage blocks downgrade, stale profile revision, notification list growth, audit sensitive fields.

## Open questions
Any storefront slug mutation detail not already resolved by PD-052 must be surfaced rather than guessed.

## Completion report
Record endpoint contracts, role behavior and verification.
