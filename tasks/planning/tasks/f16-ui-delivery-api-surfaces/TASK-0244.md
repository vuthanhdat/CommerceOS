## Objective
Create the reusable frontend foundation for `apps/storefront` and `apps/backoffice` so feature screens share routing, HTTP/error handling, pagination, authorization presentation, forms and test conventions rather than implementing them ad hoc.

## Scope
- Route-level layouts and navigation foundation.
- Typed HTTP wrapper with configurable API base URL.
- RFC 7807/ProblemDetails mapping and normalized client error types.
- Cursor-pagination helper.
- Idempotency-key helper for browser mutations where the API requires it.
- Revision-conflict/stale-data handling pattern.
- Standard loading, empty, validation, forbidden, not-found, conflict and service-unavailable states.
- Capability-aware navigation/action guard abstraction; it is presentation only, not authorization.
- Accessible base components needed by planned screens: page shell, table, form field, dialog, status badge, pagination/load-more, alert/error panel.
- Responsive layout baseline.
- Unit/component test setup and documented feature-folder convention.

## Out of scope
Authentication implementation, merchant Tenant selection, business screens, domain/API implementation, speculative global state framework, speculative generated API client or design-system package extraction.

## Inputs
`apps/storefront`, `apps/backoffice`, F16 plan, architecture rules, ADR-012, current API ProblemDetails setup.

## Expected changes
Shared/local frontend utilities and components inside the existing apps or a repository-local shared package only if actual duplication justifies it; package dependencies where clearly required; tests and short developer documentation.

## Implementation steps
1. Inspect current app entry points/build/test setup and choose the smallest routing solution compatible with both apps.
2. Define route/layout and feature-folder conventions.
3. Implement HTTP wrapper, ProblemDetails/error mapping, request cancellation and base URL configuration.
4. Implement shared page states, pagination and mutation idempotency/revision helpers.
5. Implement accessible/responsive shell primitives.
6. Add representative tests for success/error/loading/conflict/forbidden behavior.
7. Document how feature tasks should add routes, API calls and tests.
8. Run frontend builds/tests and repository harness.

## Acceptance criteria
- [ ] Both frontend apps can add real routes without custom routing infrastructure per feature.
- [ ] HTTP failures are mapped consistently, including validation, 401/403, 404, 409 and 503.
- [ ] Browser retries can preserve an idempotency key when an endpoint requires it.
- [ ] Cursor pagination and stale-revision conflict handling have reusable patterns.
- [ ] Capability guards never substitute for server authorization.
- [ ] Base components are keyboard accessible and responsive at the foundation level.
- [ ] No client-supplied `tenantId` authority helper is introduced.
- [ ] Focused frontend tests and `python scripts/harness_check.py` pass.

## Verification
Frontend build/test for both apps; representative component tests; full harness.

## Architecture / security / reliability / observability / local runtime
Keep business authority on the server. API endpoints and LocalStack addresses are configuration, not hard-coded environment assumptions. Preserve correlation/error details safe for users while avoiding sensitive payload logging.

## Risks and edge cases
Over-engineering a design system before screens exist; coupling app shell to test identity headers; hiding authorization failures as empty data; retrying non-idempotent mutations with a new key.

## Open questions
None; implementation should choose the smallest concrete libraries needed by current apps and record them in package manifests.

## Completion report
Record chosen routing/client conventions, packages added, tests run and any follow-up discovered by the first real feature screen.
