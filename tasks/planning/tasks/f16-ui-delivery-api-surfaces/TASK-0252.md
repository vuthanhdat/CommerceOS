## Objective
Implement merchant Sales screens for order history, operational Order inspection/cancellation and explicit refund request/review.

## Screens
- BO-20 `/app/sales/orders`.
- BO-21 `/app/sales/orders/{id}`.
- BO-22 `/app/sales/refunds` and refund detail/dialog as appropriate.

## Required UI behavior
Order list: order id, guest/customer summary, status, total, created time, status/date filters and cursor pagination. Order detail: immutable guest snapshot, lines/unit price/line total/order total, status/revision, payment/allocation/workflow/refund summaries and permitted actions. Refunds: id/order/payment/amount/lines/status/request/decision metadata and role-gated request/approve/reject.

## Acceptance criteria
- [ ] Order history is usable without treating mutable Catalog/Customer data as historical Order truth.
- [ ] Detail clearly separates Sales status from downstream payment/inventory/refund progress.
- [ ] Cancel action is offered only for plausible states but server conflict remains authoritative.
- [ ] Refund request and decision flows reflect current role policy and terminal states.
- [ ] PII is displayed only where needed and is not copied into client logs/analytics.
- [ ] Projection lag/NeedsAttention/OutcomeUnknown is represented as uncertainty rather than failure when applicable.
- [ ] Loading/empty/forbidden/not-found/conflict states and responsive tables are covered.
- [ ] Browser tests cover order view, cancel conflict and refund approve/reject path.
- [ ] Full harness passes.

## Verification
Backoffice component/browser tests against local API, frontend build, full harness.

## Architecture / security / reliability / observability / local runtime
UI is read/command delivery only. It must not resolve payment/inventory/refund discrepancies by writing another domain. Use safe correlation links for support where exposed.

## Risks and edge cases
Large orders, rapid workflow transitions, stale revision, terminal refund decisions, delayed refund progress.
