## Objective
Provide tenant-scoped Order and Refund HTTP read models plus merchant command endpoints needed by Sales Backoffice without cross-module persistence shortcuts.

## Scope
- Order list with cursor, status filter and stable created/observed timestamp suitable for UI.
- Order detail with immutable lines, guest snapshot, total, status, revision and workflow/process metadata safe for merchants.
- Explicit composition/query for payment, inventory allocation/reservation/workflow and refund summaries where required by BO-21; compose through owner contracts/projections only.
- Cancel Order HTTP command with revision/source identity.
- Refund list/detail queries.
- Request refund and Owner/Admin approve/reject endpoints using existing authority.
- Refund progress projection where useful.

## Candidate HTTP surface
`GET /api/v1/sales/orders`; `GET /api/v1/sales/orders/{id}`; `POST .../{id}/cancel`; `GET /api/v1/sales/refunds`; `GET .../refunds/{id}`; `POST .../orders/{id}/refunds`; approve/reject actions.

## Acceptance criteria
- [ ] Order list/detail are tenant-scoped and never expose another Tenant's guest/contact data.
- [ ] Historical Order lines/contact/commercial snapshot remain immutable and self-contained.
- [ ] UI timestamp fields are backed by authoritative evidence/read projection, not generated on read.
- [ ] Payment/inventory/workflow summaries use explicit contracts/projections, never foreign-table reads.
- [ ] Cancellation follows current pre-Fulfilled rules and does not claim downstream compensation is already complete.
- [ ] Refund role mapping remains Owner/Admin/Staff request; Owner/Admin approve/reject; Viewer neither.
- [ ] Refund list/detail preserve terminal decision history and progress semantics.
- [ ] HTTP conflict/not-found/forbidden mappings are tested.
- [ ] Full harness passes.

## Verification
Sales/refund application tests, HTTP tenant/authorization tests, read-model integration tests, LocalStack persistence where applicable, full harness.

## Architecture / security / reliability / observability / local runtime
Guest contact data is sensitive; avoid broad logging. Preserve correlation/source identities and at-least-once semantics of downstream effects. LocalStack only.

## Risks and edge cases
Order transitions while detail page is open; cancellation races; refund decision races; payment OutcomeUnknown; progress projection lag.

## Open questions
If no authoritative Order created-time evidence exists in current storage, add it to an owner-produced read projection without rewriting accepted Order business semantics.

## Completion report
Record final order/refund DTOs, composition contracts and verification.
