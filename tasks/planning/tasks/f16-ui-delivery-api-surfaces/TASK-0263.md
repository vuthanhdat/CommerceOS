## Objective
Create an explicitly separate Platform Admin/support delivery surface and UI for platform health, Tenant support/lifecycle and security audit without reusing merchant authority or bypassing module ownership.

## Scope
### HTTP/support contracts
- Platform health/readiness using existing readiness snapshot.
- Tenant support list/search projection; current implementation already supports Tenant get but list must be added through platform-owned/support-safe contract.
- Tenant detail composition with safe profile/status/subscription/support metadata.
- Suspend/reactivate commands requiring operation id, expected revision and reason, preserving Audit evidence.
- Platform security Audit read endpoint using explicit security-audit authority.
- Operational failure/DLQ/workflow/crawler summaries only where existing operator diagnostic tooling exposes safe support contracts; never query module tables directly for a dashboard.

### UI
- PA-01 `/platform` Platform dashboard.
- PA-02 `/platform/tenants` Tenant list.
- PA-03 `/platform/tenants/{tenantId}` Tenant detail/support actions.
- PA-04 `/platform/audit` Security audit.

## Acceptance criteria
- [ ] Platform routes use explicit platform admin/support authority and cannot be entered through normal merchant context alone.
- [ ] Tenant list/detail expose only support-safe fields.
- [ ] Suspend/reactivate always require reason and expected revision and create/retain Audit intent/evidence.
- [ ] Merchant mutation APIs cannot be used as a platform-support persistence bypass.
- [ ] Operational dashboard uses existing diagnostic/support contracts and identifies data freshness/partial availability.
- [ ] Security Audit requires explicit audit access and avoids sensitive payload disclosure.
- [ ] Loading/empty/error/forbidden/conflict states are implemented.
- [ ] Platform HTTP/UI security tests, browser tests and full harness pass.

## Verification
Platform/Tenancy/Audit tests, HTTP privileged-context tests, browser support journey, LocalStack diagnostic integration where applicable, full harness.

## Architecture / security / reliability / observability / local runtime
This is a privileged boundary distinct from Merchant Access. All privileged actions are auditable. No real AWS Console/API dependency is introduced; LocalStack diagnostics/support tooling remain the runtime source.

## Risks and edge cases
Accidental privilege reuse, stale Tenant revision, partially unavailable diagnostics, audit leakage, large Tenant list.

## Open questions
Do not invent aggregate cost/usage administration beyond existing approved diagnostics/usage contracts.

## Completion report
Record platform authority adapter, routes/screens, privileged-action tests and verification.
