## Objective
Provide the trusted authenticated delivery boundary required by Merchant Backoffice: current subject, active memberships, intentional Tenant selection and server-revalidated current Tenant context, then wire the Backoffice shell to it.

## Scope
- Delivery adapter from verified identity evidence to current subject.
- Tenant membership list suitable for tenant selection.
- Intentional current-Tenant selection when the subject has multiple memberships.
- Server-side revalidation of selected Tenant + Membership on every protected merchant request or through an equivalently safe request context.
- Current merchant context response containing safe Tenant profile/status, Membership role/status and UI capabilities derived from approved server authority.
- Backoffice bootstrap states: unauthenticated, no membership, tenant selection required, suspended/read-only where allowed, active context.
- Local/test identity path may reuse explicit development identity configuration but must not make test headers the production architecture.

## Out of scope
Real external identity-provider deployment, shopper authentication, inventing new roles/permissions, client-provided tenant authority, platform admin authentication.

## Candidate HTTP surface
- `GET /api/v1/me`
- `GET /api/v1/me/memberships`
- `POST /api/v1/me/current-tenant` or an equivalent server-validated selection mechanism
- `GET /api/v1/merchant-context`

Exact delivery mechanics may differ after code inspection, but the trust invariant may not.

## Acceptance criteria
- [ ] A subject with one active membership enters the correct Tenant context without trusting a request `tenantId`.
- [ ] A subject with multiple active memberships must intentionally select one and the server revalidates it.
- [ ] Disabled membership cannot become active authority through stale browser state.
- [ ] Tenant suspension behavior matches the approved merchant read/mutation authority rules.
- [ ] Current context exposes only safe UI information and role/capability presentation data.
- [ ] Backoffice route shell handles unauthenticated/no-membership/select-tenant/forbidden states explicitly.
- [ ] Cross-tenant tampering tests fail closed.
- [ ] Test-only identity support is explicit configuration and cannot silently enable in normal runtime.
- [ ] Focused security/integration tests and full harness pass.

## Verification
Tenancy application tests, HTTP authorization tests, cross-tenant tests, Backoffice shell tests, configured LocalStack integration where persistence is involved, full harness.

## Architecture / security / reliability / observability / local runtime
This task is a security boundary. Tenant authority is derived from current authenticated Membership and Tenant state. Correlation IDs should flow into downstream trusted contexts. LocalStack remains the only runtime target; no real AWS identity service is required.

## Risks and edge cases
Membership disabled between page load and mutation; Tenant suspended after selection; two browser tabs selecting different Tenants; stale selected Tenant after membership change.

## Open questions
Implementation may choose cookie/session/header mechanics appropriate to the current local architecture, but must not weaken the trusted-context invariant.

## Completion report
Record the merchant-context contract, selection mechanism, test identity behavior and security tests.
