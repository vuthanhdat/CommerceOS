## Objective
Provide tenant-scoped merchant Catalog list/detail read models and HTTP commands required by Products, Product Editor and Categories/Brands screens.

## Scope
- Product list/query with search, lifecycle/category/brand filters and cursor pagination.
- Product detail including name, SKU, slug, base price, lifecycle, category, brand, specifications, media and revision.
- Category and Brand list queries.
- HTTP delivery for create/change/publish/unpublish/archive.
- Explicit HTTP/application delivery for assigning references, setting specifications and setting media.
- Response metadata required for optimistic revision handling.

## Candidate HTTP surface
`GET/POST /api/v1/catalog/products`; `GET/PATCH /api/v1/catalog/products/{id}`; lifecycle actions under product; `PUT .../references`, `.../specifications`, `.../media`; `GET/POST /api/v1/catalog/categories`; retire action; equivalent Brand endpoints.

## Acceptance criteria
- [ ] All reads/mutations derive Tenant from trusted merchant context.
- [ ] Product list/detail contain exactly the fields needed by BO-10/BO-11 without foreign persistence reads.
- [ ] Archived/lifecycle/SKU/revision rules remain domain-owned.
- [ ] Category/Brand list supports active/retired presentation.
- [ ] Media mutation validates managed ready assets through existing owner contracts.
- [ ] Revision conflicts map consistently to HTTP 409/client refresh behavior.
- [ ] Cross-tenant and role/mutation authorization tests pass.
- [ ] Full harness passes.

## Verification
Catalog application tests, HTTP tests, tenant/authorization tests, LocalStack persistence integration where applicable, full harness.

## Architecture / security / reliability / observability / local runtime
Do not expose domain persistence entities as an accidental public API contract. Preserve tenant isolation and correlation; LocalStack only.

## Risks and edge cases
Stale revision, SKU/slug conflict, retired references, missing media, publication prerequisites.
