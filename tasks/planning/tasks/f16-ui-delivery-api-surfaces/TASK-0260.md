## Objective
Implement explicit Customer profile management and the approved scheduled Product promotional-price screen in Merchant Backoffice.

## Screens
- BO-61 `/app/customers` and `/app/customers/{id}`.
- BO-62 `/app/pricing/promotions` with create/schedule dialog and detail/cancel action.

## Required UI behavior
### Customers
List/search CustomerId, DisplayName, Email, Phone, preferences and revision; create/edit explicit profiles; clearly avoid language implying guest orders are automatically linked or deduplicated by email/phone.

### Promotions
List Product, immutable final promotional VND price, EffectiveFrom/Until in Tenant-friendly timezone presentation, derived Upcoming/Active/Expired/Cancelled state, current base price/effective benefit where available, and cancellation. Schedule form selects one Published Product, final promo price and finite start/end; no percentage/fixed-discount formula, stacking or editable Draft UI.

## Acceptance criteria
- [ ] Customer create/edit/list/search works against real API and handles stale revision.
- [ ] Guest checkout/customer identity remains explicitly separate; no auto-link UI behavior is introduced.
- [ ] Promotion form uses final promotional unit price, not discount percentage/amount.
- [ ] Schedule times are presented in Tenant timezone while API uses unambiguous instants and invalid/ambiguous server validation is surfaced.
- [ ] Promotion terms cannot be edited after acceptance; change flow is Cancel + create new Promotion.
- [ ] Adjacent schedules are allowed where server accepts them; overlap conflicts are explained.
- [ ] Staff/Viewer mutation controls are presentation-gated and server remains authoritative.
- [ ] Current non-beneficial Promotion is represented without implying cancellation or a shopper price increase.
- [ ] Responsive/accessibility/component/browser tests and full harness pass.

## Verification
Backoffice component/browser tests, Customer edit conflict test, Promotion schedule/cancel/time-boundary journey, frontend build, full harness.

## Architecture / security / reliability / observability / local runtime
Do not expose Customer PII in logs. Do not let frontend calculate authoritative Pricing decisions; server remains authority.

## Risks and edge cases
DST/wall-clock ambiguity, base-price changes, cancellation race, customer duplicate contact values, long search results.

## Open questions
None; new CRM/promotion features require separate product decisions.

Record routes, UX rules and tests.
