## Objective
Implement the first complete shopper journey in `apps/storefront`: product listing -> product detail -> transient cart -> authoritative checkout/reconfirmation -> order confirmation.

## Screens
- SF-01 `/{storefrontSlug}` Product listing.
- SF-02 `/{storefrontSlug}/products/{productSlug}` Product detail.
- SF-03 `/{storefrontSlug}/cart` Cart.
- SF-04 `/{storefrontSlug}/checkout` Checkout.
- SF-05 `/{storefrontSlug}/order-confirmation/{orderId}` immediate confirmation state.

## Required UI behavior
- Listing: store identity, search, product image/name/SKU, base/effective price, promotion presentation, availability, classification, add-to-cart and cursor load-more.
- Detail: gallery, specifications, availability, price/promotion, quantity and add-to-cart.
- Cart: browser-local lines, quantity/update/remove/clear and clearly labelled estimated totals.
- Checkout: guest name/email required; phone/address optional where contract allows; validate before placement; show authoritative changed price and require explicit reconfirmation.
- Placement: reuse one idempotency key for the same submission attempt and prevent double-click duplicate intent.
- Confirmation: render accepted immutable lines/total/order id/status from placement result; do not invent insecure anonymous order lookup.

## Acceptance criteria
- [ ] Shopper can complete the full approved guest journey against real F16 HTTP endpoints.
- [ ] Cart state is transient/untrusted and never presented as authoritative price truth.
- [ ] Price/promotion display follows Pricing first-slice rules.
- [ ] Reconfirmation UI is explicit and no Order is created by the changed-price validation attempt.
- [ ] Loading/empty/not-found/suspended/unavailable/validation/conflict/service-unavailable states are usable.
- [ ] Product images have appropriate alt text and forms/navigation are keyboard accessible.
- [ ] Mobile and desktop layouts are functional.
- [ ] Component tests cover cart behavior and checkout reconfirmation; browser E2E covers one successful order and one price-change flow.
- [ ] Full harness passes.

## Verification
Storefront unit/component tests, browser E2E against configured local APIs/LocalStack, frontend build, full harness.

## Architecture / security / reliability / observability / local runtime
The UI never sends a trusted Tenant identity. It uses storefront slug and server-owned public context. Preserve server correlation/error codes where useful and never log guest contact details unnecessarily.

## Risks and edge cases
Refresh during checkout; duplicate submit; product removed from cart authority; price or stock changes; unavailable image; long product names/specifications; small mobile viewport.
