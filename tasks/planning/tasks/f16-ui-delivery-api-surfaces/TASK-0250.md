## Objective
Expose the tenant-facing source/enrollment/import-candidate read surfaces missing from PDI and implement the Backoffice Product Import experience without allowing external source data to silently mutate canonical Catalog Products.

## Screen
BO-13 `/app/catalog/import` with Source Registry/Enrollment, Manual URL Import and Candidate Review sections.

## Backend/API scope
- List platform-eligible sources and current Tenant enrollment state.
- Enable approved source for Tenant using existing governance authority.
- Manual URL ingestion request endpoint with idempotency.
- ImportCandidate list/search/status filter and detail read.
- Approve/reject/apply HTTP commands using existing review service.
- Safe ingestion work/run status projection if current persistence/evidence supports it; do not fabricate percentage progress.

## Candidate HTTP surface
`GET /api/v1/product-data/sources`; `POST .../sources/{id}/enable`; `POST /api/v1/product-data/manual-ingestions`; `GET /api/v1/product-data/import-candidates`; `GET .../{id}`; approve/reject/apply actions.

## Required UI information/actions
Source name/eligibility/enabled state; URL form; candidate source/product identifiers, proposed name/SKU/VND price, current status/revision/provenance and review note; approve/reject/apply actions only when eligible.

## Acceptance criteria
- [ ] Tenant source enablement cannot override platform source policy or subscription entitlement checks.
- [ ] Manual URL input is constrained by server policy and UI explains server rejection without bypass suggestions.
- [ ] Candidate queue/list and detail are tenant-scoped and expose provenance needed for merchant review.
- [ ] Approve/reject/apply follow current revision/status rules and never auto-apply source changes.
- [ ] UI displays Ready/Approved/Applied/Rejected/Superseded accurately.
- [ ] No external source image/hotlink behavior is invented beyond approved Files/Media policy.
- [ ] Focused PDI/HTTP/UI tests and full harness pass.

## Verification
PDI application/HTTP tests, candidate authorization/revision tests, Backoffice component/browser tests, configured LocalStack queue/persistence tests where applicable, full harness.

## Architecture / security / reliability / observability / local runtime
Source policy remains platform authority; Catalog remains canonical Product authority. External failures are observable with safe reason codes. LocalStack-only runtime.

## Risks and edge cases
Candidate becomes stale after merchant Product edit; source disabled after queueing; scheduled entitlement revoked; duplicate manual request.

## Open questions
Only expose run-status fields already backed by authoritative evidence; do not invent operational semantics for UI convenience.

## Completion report
Record added list/query contracts, endpoints, screen sections and verification.
