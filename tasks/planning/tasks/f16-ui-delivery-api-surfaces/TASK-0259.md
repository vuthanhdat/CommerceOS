## Objective
Expose the completed Customer/CRM and first Pricing/Promotion capabilities through merchant HTTP/read models suitable for Customers and Promotions screens.

## Customer scope
- Tenant-scoped list/search/get/create/update endpoints over existing `CustomerProfileService`.
- Fields: CustomerId, DisplayName, Email, Phone, email/sms opt-in preferences, Revision.
- No guest-order auto-creation/matching; no implicit identity merge.
- Optional Order association/history only if an existing explicit owner contract already supports it; otherwise keep it out of this task.

## Pricing scope
- Promotion list/detail projection by Tenant/Product with immutable scheduled final VND price, EffectiveFrom/Until, derived temporal state, cancellation evidence and whether it is currently beneficial versus current Catalog base price.
- Schedule and cancel HTTP commands using existing Promotion authority; Owner/Admin only.
- Product selector/read information through Catalog contract, not Catalog persistence.
- Preserve schedule no-overlap and immutable accepted terms.

## Candidate HTTP surface
`GET/POST /api/v1/customers`; `GET/PATCH /api/v1/customers/{id}`; `GET/POST /api/v1/pricing/promotions`; `GET /api/v1/pricing/promotions/{id}`; `POST .../{id}/cancel`.

## Acceptance criteria
- [ ] Customer reads/writes are tenant-isolated and guest checkout remains independent.
- [ ] Duplicate contact values are not silently treated as identity uniqueness unless existing Customer rules say so.
- [ ] Customer update uses revision conflict handling.
- [ ] Promotion list/detail derives Upcoming/Active/Expired/Cancelled presentation from authoritative immutable terms/cancellation/time without introducing editable Draft.
- [ ] Only Owner/Admin can schedule/cancel; Staff/Viewer remain forbidden server-side.
- [ ] Scheduling cannot target an ineligible/non-Published Product or create overlap.
- [ ] Current-benefit presentation reflects `min(current base price, promotional price)` semantics and never raises price.
- [ ] HTTP tenant/role/revision/overlap/time tests and full harness pass.

## Verification
Customer/Pricing application and HTTP tests, cross-tenant/authorization tests, Pricing time/overlap regression, LocalStack persistence, full harness.

## Architecture / security / reliability / observability / local runtime
Customer contact data is sensitive. Pricing remains separate authority from Catalog/Sales. HTTP delivery must not reopen PD-054 or create a discount engine. LocalStack only.

## Risks and edge cases
Customer concurrent edit, base-price change while Promotion active, cancellation during checkout, non-beneficial active Promotion, adjacent schedule boundaries.

## Open questions
No new CRM order-link or promotion semantics may be invented in this task.

## Completion report
Record Customer/Promotion endpoints, projection fields and verification.
