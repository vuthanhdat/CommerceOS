## Objective
Verify F16 as a coherent product delivery milestone rather than a collection of independently working screens, and harden browser behavior, accessibility, authorization, failure handling and LocalStack end-to-end journeys.

## Scope
- Cross-app browser E2E against configured local APIs and LocalStack.
- Merchant multi-Tenant selection/authorization regression.
- Storefront browse -> cart -> checkout -> Order flow.
- Merchant Product create/publish -> Storefront visibility.
- Order/refund and Inventory operational flows.
- Procurement -> receipt/invoice evidence path where stable.
- Accounting/reporting visibility after business facts/projection lag.
- Customer and Promotion merchant journeys.
- Team/subscription/notification/audit flows.
- Platform Tenant support privileged flow.
- Accessibility pass for keyboard navigation, labels, dialogs, focus, status/error announcements and basic contrast issues discoverable by available automated/manual checks.
- Responsive checks on representative mobile/tablet/desktop widths.
- Loading/empty/403/404/409/503 and stale-revision/idempotency/reconfirmation behavior.
- Frontend bundle/build hygiene and removal of demo-only dead screens/state.
- Update developer docs/runbook for starting API + Storefront + Backoffice + required LocalStack services.

## Acceptance criteria
- [ ] One automated E2E demonstrates merchant Product publication becoming visible on Storefront and completing guest checkout.
- [ ] Cross-Tenant browser/API tampering is denied.
- [ ] Double-submit and price-reconfirmation flows do not create duplicate Orders.
- [ ] Stale revisions are handled without silent overwrite across representative merchant mutations.
- [ ] Critical screens have usable keyboard navigation and explicit accessible names/status feedback.
- [ ] Representative layouts work on small and large viewports without hiding required actions/data.
- [ ] 401/403/404/409/503 and projection-lag states are intentionally tested on representative routes.
- [ ] No frontend code contains LocalStack/AWS SDK persistence shortcuts, hard-coded real-AWS targets or client `tenantId` authorization assumptions.
- [ ] Demo-only code replaced by real routes is removed or clearly isolated.
- [ ] Frontend builds/tests, selected configured-LocalStack E2E and `python scripts/harness_check.py` pass.

## Verification
Full frontend unit/component/browser suite, targeted backend HTTP/integration regressions, LocalStack E2E, full repository harness.

## Architecture / security / reliability / observability / local runtime
Treat this as a milestone verification task, not an excuse to patch business rules into UI. Defects discovered in owner-domain semantics/contracts should be fixed in the owning module/task scope and protected by tests. LocalStack remains the only runtime target.

## Risks and edge cases
Flaky browser timing against eventual projections, test data isolation, port/resource collision between parallel task instances, overly broad E2E tests that hide unit-level failures.
