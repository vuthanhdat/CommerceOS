## Objective
Implement Sales-owned RefundRequested -> RefundApproved/RefundRejected review with eligibility bounds, expected revision and idempotency.

## Scope
Refund request aggregate/state; eligible Order/payment/issue references; approved amount/whole-unit returned quantities bounded by original evidence; list/review UI/API; role authorization per TASK-0210; audit intent; terminal decision.

## Out of scope
Inventory return, provider refund, Accounting correction before approval.

## Inputs
PD-023, Sales access patterns and resolved role mapping.

## Expected changes
Sales Domain/Application/Infrastructure/back-office review surface/tests.

## Implementation steps
Implement request eligibility/idempotency, review list, approve/reject commands with revision/auth and immutable decision data, persist approved consumer-required payload/outbox placeholder.

## Acceptance criteria
- [x] RefundRequested alone produces no stock/payment/accounting effect.
- [x] One logical request reaches at most one terminal approval decision.
- [x] Approved amount/quantity cannot exceed eligible original evidence.
- [x] Only resolved authorized roles can approve/reject.
- [x] Duplicate approve/reject is safe; conflicting terminal decision rejected.
- [x] Audit intent for privileged decision is durable.

## Verification
Domain/authorization/persistence/idempotency/UI contract/harness.

## Architecture / security / reliability / observability / local runtime
Sales owns review state only; no foreign persistence reads. Decision/correlation/source references recorded.

## Risks and edge cases
Concurrent duplicate review action and order correction history.

## Open questions
Non-restock refund remains out of MVP.

## Completion report
Record review lifecycle tests.
