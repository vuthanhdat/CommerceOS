## Objective
Consume RefundApproved independently so Inventory records one restockable StockReturned and Payments executes/reconciles one provider refund operation.

## Scope
Inventory source claim/eligible original issue validation/OnHand return/movement/StockReturned fact; Payments approved-refund identity, cumulative cap, provider idempotency, timeout Unknown, query/reconcile, PaymentRefunded fact.

## Out of scope
Non-restock returns, Inventory inferring payment result, Payments inferring stock return.

## Inputs
ADR-011, Inventory/Payments refund contracts.

## Expected changes
Inventory/Payments consumers, provider refund adapter/tests, outboxes.

## Implementation steps
Implement each consumer with source inbox, owner validation and atomic effect; provider refund operation/reconciliation; publish owned follow-up facts; test duplicates/out-of-order/partial consumer failures.

## Acceptance criteria
- [x] RefundApproved replay produces at most one StockReturned and one logical provider refund operation.
- [x] Returned quantity is an explicit approved original-issue quantity and increases OnHand exactly once.
- [x] Payments cumulative verified refunds cannot exceed captured amount.
- [x] Provider timeout remains OutcomeUnknown and blocks unsafe duplicate refund.
- [x] Only verified provider evidence can produce the PaymentRefunded owner fact.
- [x] Inventory/Payments failures recover independently and never read Sales persistence.

## Verification
Domain/consumer/provider failure/E2E duplicate/out-of-order/LocalStack/harness.

## Architecture / security / reliability / observability / local runtime
Stable source/provider identities; correlation spans refundApprovalId through owner effects.

## Risks and edge cases
Provider callback before request response; return consumer delayed while payment refund succeeds.

## Open questions
None for restockable MVP.

## Completion report
Completed 2026-08-14: Inventory now consumes explicit approved-return facts through stable source identities and its existing conditional stock-operation boundary. Payments has a tenant/payment-owned durable refund ledger with one provider operation per approval, cumulative captured-amount cap, Unknown blocking, and reconciliation. The LocalStack foundation routes RefundApproved independently to Inventory, Payments, and Accounting queues.
