## Objective
Consume RefundApproved independently so Inventory records one restockable StockReturned and Payments executes/reconciles one provider refund operation.

## Scope
Inventory source claim/eligible original issue validation/OnHand return/movement/StockReturned fact; Payments approved-refund identity, cumulative cap, provider idempotency, timeout Unknown, query/reconcile, PaymentRefunded fact.

## Out of scope
Non-restock returns, Inventory inferring payment result, Payments inferring stock return.

## Inputs
ADR-011, Inventory/Payments refund contracts.

## Expected changes
Inventory/Payments consumers, provider refund adapter/tests, outboxes.

## Implementation steps
Implement each consumer with source inbox, owner validation and atomic effect; provider refund operation/reconciliation; publish owned follow-up facts; test duplicates/out-of-order/partial consumer failures.

## Acceptance criteria
- [ ] RefundApproved replay produces at most one StockReturned and one logical provider refund operation.
- [ ] Returned quantity cannot exceed eligible original issued quantity and increases OnHand exactly once.
- [ ] Payments cumulative verified refunds cannot exceed captured amount.
- [ ] Provider timeout remains OutcomeUnknown and blocks unsafe duplicate refund.
- [ ] Only verified evidence creates PaymentRefunded.
- [ ] Inventory/Payments failures recover independently and never read Sales persistence.

## Verification
Domain/consumer/provider failure/E2E duplicate/out-of-order/LocalStack/harness.

## Architecture / security / reliability / observability / local runtime
Stable source/provider identities; correlation spans refundApprovalId through owner effects.

## Risks and edge cases
