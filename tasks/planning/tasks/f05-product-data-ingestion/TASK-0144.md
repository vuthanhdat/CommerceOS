## Objective
Refresh known mapped source products on schedule only while current source governance and ScheduledProductIngestion entitlement both permit dispatch.

## Scope
Schedule config/state; create/enable/disable; dispatch due mapped sources; entitlement + platform/Tenant policy recheck at dispatch; queue work; bounded concurrency; change/history observations.

## Out of scope
Discovery/category crawl, automatic Catalog update, guaranteed wall-clock SLA.

## Inputs
PDI/source policy, entitlement contract, queue from TASK-0142.

## Expected changes
PDI scheduler/dispatcher/infrastructure tests; use LocalStack-supported scheduler mapping only when sufficient.

## Implementation steps
Model schedule state, check entitlement at create/enable and every dispatch, enqueue stable work identities, suppress without deleting history after entitlement/policy loss, test duplicate schedules/dispatch.

## Acceptance criteria
- [ ] Starter cannot enable/run scheduled ingestion; Trial/Growth/Business can only if source policy also permits.
- [ ] Losing entitlement/policy suppresses future dispatch without deleting PDI history/config.
- [ ] Duplicate scheduler delivery does not duplicate logical source snapshot work.
- [ ] Dispatch remains bounded/backpressured through existing queue.
- [ ] Unsupported LocalStack scheduler behavior is documented and nearest-layer tests remain authoritative.

## Verification
Unit/clock/contract + LocalStack schedule/queue where supported + harness.

## Architecture / security / reliability / observability / local runtime
No plan-name checks; schedule diagnostics expose due/suppressed reasons safely.

## Risks and edge cases
Timezone/scheduler emulator differences; stale mapped source.

## Open questions
Schedule cadence should be configured by product/source policy; do not hard-code unapproved external request frequency.

## Completion report
Implemented tenant-scoped scheduled refresh configuration and dispatch with a
fresh platform-policy, tenant-enrollment and `ScheduledProductIngestion`
entitlement recheck on every due run. Suppression retains schedule/history;
stable due-window work identities make repeated scheduler delivery safe. The
application dispatcher remains the authoritative LocalStack-tested boundary;
no EventBridge Scheduler fidelity is claimed.
