## Objective
Promote recurring/high-impact review checks discovered during implementation into stable executable repository guardrails and a predictable verification entry point.

## Scope
Dependency rules; tenant repository/API conventions where mechanically detectable; event envelope/version/idempotent consumer conventions; Accounting/Inventory invariant tests; CDK source-of-truth/config boundaries; bootstrap/reset checks; evolve `tools/commerceos.py check` modes if warranted while preserving harness compatibility.

## Out of scope
Brittle lint for every prose rule, bypassing valid failures, replacing focused tests with one giant slow suite.

## Inputs
Architecture-test backlog, TASK-0232 defect/review findings, harness improvement process.

## Expected changes
Architecture/static tests, harness/tooling/CI docs.

## Implementation steps
Rank recurring checks by impact/automation reliability, implement minimal guardrails, provide actionable diagnostics, partition fast vs LocalStack verification, document usage.

## Acceptance criteria
- [ ] Repeated critical architecture mistakes have mechanical checks where practical.
- [ ] Fast check remains deterministic and useful for inner loop.
- [ ] LocalStack mode is explicit/isolated and does not silently contact AWS.
- [ ] Guardrail failures identify actionable rule/source.
- [ ] No valid check is weakened solely to pass current code.
- [ ] CI and humans can call stable repository-owned verification commands.

## Verification
Self-test guardrails with representative forbidden/allowed project structures where practical; CI/harness.

## Architecture / security / reliability / observability / local runtime
Harness is quality mechanism, not business code. Bound expensive local integration volume.

## Risks and edge cases
Overfitting to current filenames/project graph.

## Open questions
Keep `scripts/harness_check.py` as stable entry until migration is intentionally complete.

## Completion report
