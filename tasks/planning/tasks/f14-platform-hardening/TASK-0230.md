## Objective
Make critical API/worker/workflow/provider/crawler/accounting failure states diagnosable through consistent structured correlation and bounded metrics in the LocalStack runtime.

## Scope
Logging conventions; correlation/causation propagation; tenant-safe structured fields; latency/error/retry/DLQ/Unknown/NeedsAttention metrics; CloudWatch-style LocalStack mapping where useful; diagnostic commands/docs.

## Out of scope
Business state in logs, secrets/raw payment/provider/crawler payloads, production-SLA claims from emulator metrics.

## Inputs
NFR observability, technical baseline and existing logging implementation.

## Expected changes
Shared technical observability utilities/config/tests and module adoption where high-value.

## Implementation steps
Inventory current logs, define stable fields, propagate IDs through HTTP/events/workflows/provider calls, add metrics for named operational states, verify inspect/diagnostic tooling.

## Acceptance criteria
- [ ] Critical flows can be traced across producer/relay/consumer/provider by correlation/causation/source IDs.
- [ ] Logs do not expose secrets, raw tokens or cross-Tenant private data unnecessarily.
- [ ] Payment/charge OutcomeUnknown and NeedsAttention are directly diagnosable.
- [ ] Queue/DLQ/retry and crawler/provider failure counts are observable where introduced.
- [ ] Emulator/operational logs are never treated as business authority.

## Verification
Unit/contract/log capture; LocalStack CloudWatch-style integration if useful/supported; failure scenarios; harness.

## Architecture / security / reliability / observability / local runtime
Observability remains technical cross-cutting infrastructure. Control local log volume/retention.

## Risks and edge cases
High-cardinality IDs and sensitive structured fields.

## Open questions
Metrics backend details may follow current code; capability matters more than service imitation.

## Completion report
Record field/metric inventory and diagnostic examples.
