## Objective
Create SubscriptionBilling ownership/persistence and idempotently bootstrap the approved Trial, Starter, Growth and Business immutable terms.

## Scope
Module/table; Plan, PlanVersion, Trial terms records; version-controlled seed artifact/command; catalog query; immutable/version conflict rules.

## Out of scope

## Inputs
Subscription domain baseline, ADR-008, technical reconciliation.

## Expected changes
SubscriptionBilling Domain/Application/Infrastructure and CDK table after code inspection.

## Implementation steps
Model stable Plan/version identities and EntitlementSet terms, implement idempotent bootstrap, query sellable versions, prevent mutation of accepted versions, add persistence tests.

## Acceptance criteria
- [x] Approved values exactly match domain baseline.
- [x] Trial is dedicated terms, not Starter alias.
- [x] Re-running bootstrap is safe and incompatible mutation/version collision fails explicitly.
- [x] Runtime consumers can query catalog without hard-coded authority outside module.
- [x] No runtime Scan or external config store becomes plan authority.

## Completion report
Completed 2026-08-13.

- Created SubscriptionBilling Domain, Application, Contracts, and Infrastructure projects, plus a module-owned DynamoDB table provisioned by CDK.
- Added the version-controlled `catalog/initial-catalog.v1.json` seed: dedicated 30-day Trial terms and immutable initial Starter, Growth, and Business `v1` terms with the approved VND prices, limits, and capabilities.
- `CatalogBootstrapService` performs direct strong record reads and conditional creates. Equivalent replay reports `AlreadyApplied`; reuse of the same immutable record identity with different terms reports `VersionConflict` rather than overwriting history.
- Added producer-owned catalog query contracts. These are display/query contracts only; Plan names/values are not entitlement authority, which remains the later `EntitlementSet` boundary.
- The LocalStack configuration now derives and exposes the SubscriptionBilling table name from the task instance. The repository lifecycle invokes the bootstrap command after CDK deployment, so each clean LocalStack instance receives the source-controlled seed without a manual resource/data prerequisite. No external configuration store or runtime Scan is used.
