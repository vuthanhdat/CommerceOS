## Objective
Implement monthly activation/upgrade/downgrade/renewal/cancel/grace/end/reactivation exactly as approved, driven only by verified PlatformCharge evidence and authoritative usage checks.

## Scope
Paid activation; billing anchors/month-end; upgrade new period after success; scheduled downgrade and BlockedByUsage; cancel renewal; definitive renewal failure -> 7-day PastDue -> Ended; reactivation new period; Unknown reconciliation.

## Out of scope
Annual billing, proration, tax/statutory invoice, Enterprise, destructive resource remediation.

## Inputs
Subscription domain baseline and provider task.

## Expected changes
SubscriptionBilling aggregate/application/persistence/workers and tests.

## Implementation steps
Implement state/intent dimensions and expected revisions/idempotency, provider charge coordination, owner usage assessment contracts, period calculations, recovery/reconcile jobs.

## Acceptance criteria
- [ ] Upgrade entitlements change only after verified successful required charge and start a fresh month.
- [ ] Downgrade is next-renewal and blocked if authoritative hard-limit usage exceeds target.
- [ ] No downgrade auto-deletes/disables foreign resources.
- [ ] Cancel renewal does not end current paid period early.
- [ ] Only definitive renewal failure creates PastDue; grace is exactly 7 days.
- [ ] Unknown never becomes failure by time passage.
- [ ] Ended preserves read/history/recovery and does not mutate Tenant/Membership.
- [ ] Reactivation creates new accepted period/history.

## Verification
Extensive unit clock tests; provider failure/reconcile integration; duplicate commands; LocalStack persistence/worker; harness.

## Architecture / security / reliability / observability / local runtime
All tenant scoped; platform admin remains read-only support. Durable operations and unknown states observable.

## Risks and edge cases
Month-end anchors, retries at period boundary, simultaneous plan-change/cancel/renewal.

None in current approved product policy.
