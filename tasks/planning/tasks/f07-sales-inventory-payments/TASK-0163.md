## Objective
Create Payments ownership for one Order payment obligation, immutable attempts, provider-operation identity and reconciliation state.

## Scope
Payments module/table; Payment aggregate; PaymentAttempt; full Order amount/currency; stable provider operation/idempotency identity; Captured/Declined/OutcomeUnknown evidence states; current get/query/reconcile ports.

## Out of scope
Provider implementation, authorize-only, split tender, partial capture, Accounting.

## Inputs
Payments domain baseline, PAY access patterns.

## Expected changes
Payments Domain/Application/Infrastructure/contracts/CDK/tests.

## Implementation steps
Model obligation and attempts, enforce amount/currency/source, block new attempt while prior Unknown, implement provider-evidence/inbox/outbox primitives and persistence tests.

## Acceptance criteria
- [ ] Exactly one Payment obligation per Order in MVP.
- [ ] Attempts remain immutable history.
- [ ] Full accepted Order Money is authoritative; provider/client cannot change it.
- [ ] New capture is prohibited while prior logical attempt is OutcomeUnknown.
- [ ] Definitive decline terminates attempt only, not automatically the obligation/Order.
- [ ] Duplicate/out-of-order evidence cannot regress/duplicate known outcome.

## Verification
Domain/persistence/tenant/source-dedupe/architecture/LocalStack/harness.

## Architecture / security / reliability / observability / local runtime
Payments stores provider evidence but no real PAN/CVV. Unknown/reconcile state observable.

## Risks and edge cases
Callback before synchronous response; duplicate provider operation.
