## Objective
Build a separate external-like provider test application with stable idempotent operations and deterministic failure/latency/webhook scenarios.

## Scope
Payment intent/capture/refund/query APIs sufficient for approved CommerceOS contracts; operation idempotency store; deterministic tokens such as success/declined/timeout-before/after-commit/delayed/500/duplicate webhook/webhook-before-response; signed webhook dispatcher; test controls.

## Out of scope
Real banking/card semantics, real PAN/CVV, becoming a helper inside Sales/Payments.

## Inputs
`docs/06-mock-payment-provider.md`.

## Expected changes
Separate provider app/deployment/persistence/queue if justified plus contract tests.

## Implementation steps
Implement provider model/API/idempotency, scenario engine, signed delivery/retry, stable query, failure controls and scenario tests.

## Acceptance criteria
- [x] Same idempotency key + equivalent request returns prior result; incompatible reuse rejects.
- [x] Timeout-after-commit can commit Captured then make caller time out.
- [x] Delayed/duplicate/out-of-order webhook scenarios are deterministic.
- [x] Provider query reveals committed state for reconciliation.
- [x] Webhook delivery failure is independently retryable/DLQ-capable when queue mapping is introduced.
- [x] No real payment data is accepted/stored.

## Verification
Provider unit/contract/E2E scenario tests; LocalStack infra where used; harness.

## Architecture / security / reliability / observability / local runtime
External-like boundary and test signing secret. Scenario selection/logging safe and deterministic.

## Risks and edge cases

## Completion report
Completed 2026-08-14: deterministic capture/query and DynamoDB idempotency persistence cover success, decline, timeout-before/after commit, delayed, provider error, duplicate and webhook-before-response. Webhook envelopes are signed and deterministic; no delivery queue was introduced, so retry/DLQ remains the responsibility of any future dispatcher mapping.
