## Objective
Implement the first approved Pricing & Promotion slice exactly as defined by TASK-0241 and technically designed by TASK-0242: one scheduled authoritative final promotional unit price for one Product, applied to all storefront shoppers without stacking or generic discount-engine semantics.

## Context
Catalog already owns Product base price and sellability. Storefront/Checkout already performs authoritative validation/repricing, Sales already preserves accepted Order snapshots, and Accounting/Refund consume accepted business facts. This task adds Pricing as a dedicated authority without moving those responsibilities.

## Scope
Implement only the first slice approved by TASK-0241/TASK-0242:

- Pricing module/domain/application/infrastructure boundary.
- Tenant-owned Promotion persistence and lifecycle.
- Owner/Admin create/manage operations allowed by the approved lifecycle; Staff/Viewer mutation denial.
- Concurrency-safe prevention of overlapping effective promotion periods for the same Product.
- Authoritative effective-price evaluation for storefront checkout.
- No-promotion path returning base price unchanged through the designed contract.
- Storefront/public price projection required by TASK-0241.
- Checkout repricing/reconfirmation integration using authoritative effective price.
- Immutable Sales Order pricing provenance required by TASK-0242.
- Focused observability/correlation and LocalStack-backed persistence verification.
- Regression verification that accepted effective Order amount continues to drive Accounting/refund behavior without a new discount accounting model.

## Out of scope
- Coupons or coupon codes.
- Percentage or fixed-amount discount rules.
- Manual merchant-entered checkout/order discounts.
- Category, cart or order-wide promotions.
- Customer-specific/segment pricing.
- Price lists.
- Stacking, priority resolution or generic rule-engine abstractions.
- Buy-X-Get-Y or bundle promotion behavior.
- Promotion-driven Product publication/sellability.
- Repricing existing Orders after Product/Promotion changes.
- New discount/contra-revenue accounting model.
- Separate Pricing deployment unit unless TASK-0242 has an accepted ADR explicitly requiring it.

## Implementation steps
1. Implement the approved Promotion model/lifecycle and tenant-safe mutation authority.
2. Implement persistence/access patterns exactly as designed, including protected overlap/concurrency behavior.
3. Implement authoritative effective-price evaluation with provenance.
4. Integrate Storefront/public price projection.
5. Integrate checkout so client prices/discounts remain untrusted and authoritative price changes force reconfirmation.
6. Persist immutable accepted Pricing provenance in Sales Order snapshots as designed.
7. Add focused tests for lifecycle/time boundaries, authority, tenant isolation, overlap concurrency, no-promotion path, repricing/reconfirmation and historical independence.
8. Add LocalStack integration coverage for infrastructure-sensitive persistence/concurrency behavior.
9. Run focused verification plus repository harness.

## Acceptance criteria
- [ ] Only Owner/Admin can perform approved Promotion mutations; Staff/Viewer cannot.
- [ ] Tenant isolation is enforced for all Promotion mutations/reads/evaluation paths.
- [ ] A Promotion cannot make an otherwise unpublished/archived/ineligible Product sellable.
- [ ] The authoritative first-slice result is an explicit final promotional unit price, not a generic discount expression.
- [ ] Two overlapping accepted promotion periods for the same Tenant + Product are prevented under concurrency.
- [ ] No stacking/priority/coupon/manual-discount behavior is introduced.
- [ ] Storefront public pricing matches the TASK-0241 display policy.
- [ ] Checkout ignores client discount/total authority and uses the current authoritative effective price.
- [ ] If the authoritative effective price differs from the shopper-observed price, checkout requires reconfirmation and creates no Order for that attempt.
- [ ] Sales stores the approved immutable base/effective/Promotion provenance; later Product or Promotion changes do not alter historical Orders.
- [ ] No-promotion checkout behavior remains compatible with existing base-price behavior.
- [ ] Accounting/refund regression tests prove accepted effective Order amount remains the commercial amount for this slice without a new contra-revenue model.
- [ ] No module reads/writes another module's private persistence as an integration shortcut.
- [ ] Focused tests and `python scripts/harness_check.py` pass.

## Verification
Unit/domain tests; tenant/authorization tests; interval-boundary and overlap-concurrency tests; checkout repricing/reconfirmation tests; Sales snapshot immutability tests; Accounting/refund regression tests; LocalStack integration; full harness.

## Architecture / security / reliability / observability / local runtime
Follow TASK-0242 exactly. Pricing mutations require trusted Tenant context and Merchant Access authority. Effective-price decisions must be traceable to the accepted Order correlation/provenance. LocalStack remains the only runtime/infrastructure validation target.

## Risks and edge cases
- Boundary instants around start/end time.
- Concurrent schedule creation/update.
- Product base-price edit while a Promotion is scheduled/active.
- Product unpublish/archive while Promotion remains scheduled/active.
- Promotion cancellation between cart display and checkout validation.
- Duplicate/retried merchant mutation requests if TASK-0242 requires idempotency.

## Open questions
None. If implementation discovers a material product or architecture ambiguity, stop and return it to TASK-0241 or TASK-0242 rather than invent behavior.
