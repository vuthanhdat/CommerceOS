## Objective
Refine explicit product/domain semantics for future Pricing/Promotion authority, then implement only the approved first slice without contaminating Catalog/Sales with scattered discount logic.

## Context
Product definition names Pricing/Promotion, while current MVP explicitly excludes manual guest-checkout discounts. Architecture reserves a future Pricing module.

## Scope
First perform product/domain design: offer/promotion types, eligibility, period, stacking/priority, price snapshot interaction, role/admin authority and public display. After approval, define producer-owned Pricing query used by checkout and implement the smallest approved promotion slice.

## Out of scope
Inventing coupon/discount semantics from industry convention, changing historical Order prices, making browser discount authoritative, implementation before design approval.

## Inputs
Product definition, PD-013, Catalog/Sales boundaries, TASK-0234 audit.

## Expected changes
Product decision/domain/technical docs first; then Pricing module/contracts/persistence/tests in a refined follow-up or same task only if scope remains one reviewable slice.

## Implementation steps
1. Surface unresolved policy questions and alternatives.
2. Obtain Product Owner decisions/rationale and reconcile architecture.
3. Split implementation task if resulting scope is larger than one Codex session.
4. Implement producer-owned price/offer decision and checkout integration with snapshot tests.

## Acceptance criteria
- [ ] Product semantics are explicit before application code.
- [ ] Pricing owns promotion/offer authority; Catalog retains base price and Sales retains accepted Order snapshot.
- [ ] Client discount/total is never authoritative.
- [ ] Historical Orders are never repriced by later promotion changes.
- [ ] Stacking/priority/time/eligibility behavior has deterministic tests for the approved slice.
- [ ] No generic `if plan/role/promo` logic is scattered across foreign domains.

## Verification
Docs/harness first; then domain/contract/persistence/checkout tests as refined.

## Architecture / security / reliability / observability / local runtime
Material new integration/persistence topology may require ADR after design. Tenant authority explicit.

## Risks and edge cases
Promotion engines grow quickly; split aggressively by approved scope.

## Open questions
Intentionally Needs design until future product decision.

## Completion report
Record decisions, split tasks and implementation evidence if executed.
