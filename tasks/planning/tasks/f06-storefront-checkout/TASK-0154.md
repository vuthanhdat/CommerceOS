# TASK-0154 — Implement idempotent guest Order placement and immutable snapshot

## Objective
Turn one validated/reconfirmed checkout intent into at most one logical OrderPlaced snapshot with approved guest data and durable downstream process intent.

## Scope
Checkout idempotency identity; immutable line ProductId/SKU/name/qty/unit price/currency/totals; guest name/email and conditional phone/address; OrderPlaced acceptance handoff; incompatible replay conflict.

## Out of scope
CRM auto-linking, reservation/payment workflow implementation, partial order.

## Inputs
Sales checkout rules, ADR-007 idempotency conventions, guest snapshot PD-035.

## Expected changes
Sales placement application contract/persistence entry point, storefront DTO and tests; detailed Sales module completed in TASK-0160 if separation is needed.

## Implementation steps
Define idempotency scope/request hash, validate guest fields, persist immutable accepted snapshot/operation atomically as architecture permits, return stable Order identity/status.

## Acceptance criteria
- [ ] Equivalent repeated checkout intent yields the same logical Order/result.
- [ ] Same key with incompatible request conflicts.
- [ ] Order stores authoritative accepted commercial snapshot, never browser-calculated authority.
- [ ] Guest checkout creates no CRM Customer.
- [ ] Historical snapshot is not later rewritten by Catalog/contact changes.
- [ ] Order placement does not claim stock/payment completion.

## Verification
Unit/idempotency/persistence/API contract/tenant-public context/harness.

## Architecture / security / reliability / observability / local runtime
No card data. Durable source identity/correlation required for workflow start recovery.

## Risks and edge cases
Crash after Order commit before process start; later ADR-010 start outbox must close this gap.

## Open questions
None for business placement semantics.

## Completion report
Record idempotency and snapshot evidence.
