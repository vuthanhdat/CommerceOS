## Objective
Apply confirmed Procurement receipt/correction facts to Inventory exactly once while keeping Procurement receipt truth independent of Inventory success.

## Scope
Reliable GoodsReceipt fact route/consumer queue; Inventory receive/correction source mapping; inbox/source claim; retry/DLQ; Procurement application-status projection/update via contract/fact as designed.

## Out of scope
Cross-table transaction, Procurement writing Inventory table, Accounting posting.

## Inputs
ADR-006, Procurement/Inventory contracts.

## Expected changes
Integration infrastructure and Inventory consumer/tests.

## Implementation steps
Define versioned consumer-required fact payload, publish from Procurement outbox, configure route/queue, consume idempotently into Inventory movement, test duplicate/failure/redrive.

## Acceptance criteria
- [ ] GoodsReceipt commit survives publication interruption through reliable pattern.
- [ ] Inventory applies each logical receipt quantity once.
- [ ] Duplicate/redelivered fact does not duplicate OnHand/movement.
- [ ] Failed Inventory application leaves Procurement receipt intact and becomes recoverable/actionable.
- [ ] Consumer never reads Procurement persistence.

## Verification
Contract/unit + LocalStack stream/EventBridge/SQS/DynamoDB duplicate/DLQ tests + harness.

## Architecture / security / reliability / observability / local runtime
Event tenant/source/correlation retained. Redrive preserves identity.

## Risks and edge cases
Correction arrives before original due to delivery ordering; consumer must handle or retry without corruption.

## Open questions
None.

## Completion report
Completed 2026-08-14. Inventory consumes the producer-owned confirmed GoodsReceipt fact through an explicit contract carrying product, warehouse, quantity delta, source identity and correlation. Each line maps to a source-keyed Inventory movement; duplicate delivery returns the prior effect and a failed line becomes NeedsAttention without changing Procurement receipt truth.
