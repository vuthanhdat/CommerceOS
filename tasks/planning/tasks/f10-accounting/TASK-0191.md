## Objective
Create Accounting ownership/persistence and idempotently initialize the required learning chart/control-account semantic roles for every Tenant.

## Scope
Accounting module/table; Account identity/code/status; required control roles; tenant chart bootstrap after onboarding; add/deactivate non-control accounts; immutable referenced identities; valuation-state foundation per TASK-0190 decision.

## Out of scope
Journal posting details, statutory account chart, tax compliance.

## Inputs
PD-038, resolved cost-pool decision, Accounting persistence baseline.

## Expected changes
Accounting Domain/Application/Infrastructure/CDK/bootstrap worker/contracts/tests.

## Implementation steps
Model Account/control roles, define bootstrap source/idempotency, persistence/access patterns, onboarding/tenant-created trigger contract, validation and tenant isolation tests.

## Acceptance criteria
- [x] Required Cash, Customer Deposits, Sales Revenue, Inventory, COGS, AP, GRNI, PPV and adjustment gain/loss roles exist once per Tenant.
- [x] Bootstrap replay is idempotent.
- [x] Required control accounts cannot be deactivated while capability remains enabled.
- [x] Referenced account identity/code is not reused.
- [x] Tenant cannot access another Tenant chart.
- [x] Valuation-state keying matches resolved business cost-pool scope.

## Verification
Domain/persistence/tenant isolation/LocalStack/harness.

## Architecture / security / reliability / observability / local runtime
Accounting table only; bootstrap failures recover durably and do not rewrite Tenancy.

## Risks and edge cases
Onboarding may complete before Accounting bootstrap if accounting enablement is asynchronous; merchant operation gating should follow approved capability contract, not hidden assumptions.
