## Objective
Implement Accounting's core append-only balanced journal consistency boundary with source idempotency and explicit reversal/correction.

## Scope
Journal/JournalLine values; debit=credit invariant; EffectiveDate/PostingTimestamp; source identity; post transaction; reject mutation of posted journals; reversal/compensating linkage; account eligibility; query by source/id.

## Out of scope
Automatic posting routes, user backdating/future dating, statutory period close.

## Inputs
Accounting domain baseline, PD-039.

## Expected changes
Accounting Domain/Application/Infrastructure/tests.

## Implementation steps
Model balanced draft/post semantics, transactionally persist journal + source claim, implement reversal as new balanced journal, enforce dates/account states, add duplicate/unbalanced/immutability tests.

## Acceptance criteria
- [x] Unbalanced journal cannot post.
- [x] Posted journal/lines are immutable.
- [x] Same logical source creates at most one logical posting.
- [x] Correction creates linked new reversal/compensating journal, never edits original.
- [x] EffectiveDate and PostingTimestamp remain distinct.
- [x] Tenant and account references are validated within Accounting ownership.

## Verification
Unit property tests; DynamoDB transaction/idempotency tests; tenant isolation; harness.

## Architecture / security / reliability / observability / local runtime
Journal posting is high-integrity; atomic source claim + posting required. Diagnostics expose source/correlation but not private foreign records.

## Risks and edge cases
Concurrent duplicate source consumption and reversal replay.

## Open questions
None.

## Completion report
`Journal.Create` rejects unbalanced/invalid entries; DynamoDB atomically claims the source and writes the append-only journal. Reversal flips sides into a new linked journal and tests verify the original is unchanged.
