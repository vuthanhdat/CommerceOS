# SubscriptionBilling persistence access-pattern ledger

| ID | Owner / use case | Scope | Key/query and consistency | Write protection / recovery | Cost note |
|---|---|---|---|---|---|
| SUB-AP-00 | Bootstrap immutable Trial terms and paid PlanVersions | platform catalog; no caller-selected Tenant authority | direct `CATALOG / <terms identity>` strong read; bounded `CATALOG` PlanVersion prefix Query for sellable catalog | conditional create; equal replay is `AlreadyApplied`; same identity with different contents is `VersionConflict`; no TTL | four strong reads/writes at bootstrap; one bounded Query for catalog display |
| SUB-AP-06R | Record one PlatformCharge attempt | trusted SubscriptionBilling command; Tenant id is part of the logical charge identity | strong `TENANT#<encoded> / CHARGE#<encoded logical identity>` read/create | conditional create gives one logical charge; an existing logical identity must have identical subscription, terms, and amount; no TTL | one strong read and one conditional write per first attempt |
| SUB-AP-07R | Accept provider evidence and reconcile Unknown | provider-operation identity belongs to the stored charge; provider adapter is not a merchant Payments adapter | bounded strong charge read plus transactional `EVIDENCE#...` and charge revision update | evidence id is conditionally unique; charge revision protects concurrency; settled outcomes never regress; timeout/missing evidence persists `OutcomeUnknown` | one strong read plus two transaction items per new evidence |
| SUB-AP-01R | Activate/upgrade/renew/reactivate paid subscription | trusted SubscriptionBilling command; PlanVersion selected from module-owned catalog | strong `TENANT#<encoded> / PAIDSUBSCRIPTION#CURRENT` read; conditional current/history operation transaction | stable operation id creates exactly one current transition/history item; only verified successful PlatformCharge establishes a new period | two transactional writes per accepted transition plus bounded catalog/charge reads |
| SUB-AP-04R | Schedule/revalidate downgrade, cancel renewal, PastDue, Ended | trusted Tenant command or named due worker; authoritative usage comes only through owner contract | strong current read and revision-protected current/history operation transaction | no foreign-table read or cross-domain transaction; usage excess is `BlockedByUsage`; Unknown does not create PastDue; grace is explicit seven days | two transactional writes per state transition; owner usage assessment cost remains owner-local |

The initial catalog source is `catalog/initial-catalog.v1.json`. It is SubscriptionBilling-owned platform commercial truth, not a frontend, JWT, foreign-module, AppConfig, or SSM authority. The DynamoDB key schema is module-private; no other module may read this table or depend on its record shape.

PlatformCharge records carry only SaaS commercial references, a VND whole-đồng amount, provider-operation/evidence identifiers, and outcome evidence. They never contain card, bank, or merchant-order payment data. The deterministic SaaS simulator is an Infrastructure adapter behind `IPlatformBillingProvider`; no real provider credential is required for LocalStack validation.

Paid current state and immutable operation history are separate SubscriptionBilling records. A pending downgrade stores only the target immutable terms and status; it does not copy a Membership/Warehouse count. Production composition is fail-closed for downgrade until the owning modules expose their approved usage-assessment contracts.
